企业知识库 RAG 与 Agent 开发面试准备

适用方向：AI 应用开发与 Agent 开发。

这份文档帮助你讲清项目的业务问题、工作内容、架构、实现细节和设计取舍，并通过 45 道连续追问检查理解深度。先阅读项目说明，再遮住答案进行模拟面试，最后用实践验收清单建立自己的贡献证据。

核心判断：项目实现了较完整的 RAG 应用链路，包括文档处理、混合检索、重排、引用、反馈和评测；Agent 部分是基于 LangGraph 的条件工作流，尚未形成模型自主选择多个工具的完整执行循环。

材料边界：本文基于当前源码、SQL 结构和测试文件的静态研读，未启动数据库、未调用真实模型、未完成运行性能验证。原项目实现不能直接当作个人工作成果；研究、复现、二次开发和业务上线应分别描述。建议改造都标记为待实践，不代表已经实现。

1 阅读方法与术语

第一次阅读按第 2 至第 5 章理解业务和技术。第二次从第 6 章开始练习问答。第三次按第 7 章完成独立实践，把测试记录、截图、评测报告和自己的代码改动连接起来。

先用一个熟悉的场景理解系统：把企业知识库想成一位会查资料的客服。管理员先把文件整理成便于查找的卡片；用户提问时，系统先找出相关卡片，再让大模型根据卡片组织回答。这里的 RAG 负责“先查资料再回答”，Agent 工作流负责“检查资料和回答是否够用，必要时再查一次”。这只是帮助理解的比喻，实际效果仍取决于解析质量、检索策略和模型输出。

一条问答链路可以概括成四步：文件先被解析、切分和向量化；问题进入后，系统从资料库召回候选片段；排序后把相关上下文交给模型；最后把答案、引用和反馈记录下来。第 5 章会解释各步使用的技术术语及其取舍。

2 项目介绍与业务问题

2.1 项目定位

这是一个企业知识库问答平台。管理员维护知识库、上传文件、配置模型和检索策略；用户通过问答应用查询制度、产品说明和售后资料。系统需要把多种格式的文件转成可检索知识，再根据资料生成回答，并记录依据和用户反馈。

它服务的典型问题是：企业资料多、格式杂，用户表达与文档用词不一致，单靠关键词搜索不容易找到答案；直接让大模型回答又可能缺少企业内部知识或生成无依据内容。

2.2 三十秒项目介绍

“这是一个企业知识库 RAG 平台，后端使用 FastAPI，业务数据放在 MySQL，向量数据放在 PostgreSQL 和 pgvector。文档经过解析、分块和向量化后，问答链路通过向量与 BM25 混合检索、RRF 融合及重排获取资料，再由大模型生成回答。它还使用 LangGraph 实现相关性判断和答案支撑检查，并通过用户反馈与离线评测支持策略优化。”

这段介绍讲的是项目本身。个人介绍时，应另补真实的研究、复现或改造范围。

2.3 两分钟项目介绍

“项目主要解决企业资料查找效率和问答依据问题。它把管理员侧与用户侧放在同一套前后端系统里：管理员管理文档、模型、Prompt 和检索策略，用户按问答应用进行查询。

“入库链路先按文件格式提取文本，PDF 表格转成 Markdown，无文字层的 PDF 页面使用 OCR。文本支持递归分块和父子分块，普通块与子块生成向量，父块作为回答上下文保留。

“在线链路先按策略改写查询，分别进行语义检索和 BM25 关键词检索，再用 RRF 合并排名，按需重排、回填父块和过滤低分结果。普通模式通过 SSE 输出模型增量；Agent 模式由 LangGraph 执行检索、相关性判断、生成和答案支撑检查，失败时有限重试，最后兜底。

“效果方面，项目提供四个自定义评测指标，并把点踩问题沉淀为待人工补充标准答案的评测用例。它的工程边界也很清楚：后台任务目前在应用进程内，Agent 的工具调用路径由代码固定，多知识库和知识更新一致性还存在需要改进的地方。”

2.4 用一个问题贯穿系统

假设用户问“GTE3000 超过保修期怎么维修”，资料中使用“GTE-3000”和“质保”。这只是流程示例，不代表已经验证项目对该问题的回答正确。

先看直观过程：用户用自己的说法提问，资料可能用了另一种写法。系统要先找到“说的是同一件事”的内容，再判断哪些资料最有帮助，最后把资料交给模型组织语言。每个技术步骤都在减少一种常见落差：词不一样、候选太多、片段太短或回答缺少依据。

  1. 型号写法不同，通过分词补充让两种写法都包含 gte 和 3000。
  2. “保修”与“质保”的表达差异，由向量检索补足语义匹配。
  3. 两路召回使用 RRF 合并，同一片段按 chunk_id 去重。
  4. 重排模型判断哪些候选最能回答“超期维修”问题。
  5. 如果命中子块，则回填其父块，提供收费条件等完整上下文。
  6. 资料写入 Prompt，模型生成回答，引用记录保存内容快照。
  7. 如果用户点踩，问题可以进入评测集，人工补标准答案后再回归。

4 架构与核心数据关系

4.1 系统组成

前端使用 Vue 3、Vite、Element Plus。后端使用 FastAPI 和 Pydantic，业务 ORM 是 Tortoise。LangChain 相关组件用于模型封装、文本切分和文档重排接口，LangGraph 用于状态图编排。

api/ 负责请求、鉴权和业务调用；service/ 协调模型、数据库与流程；ai/ 提供解析、切分、检索、改写、重排、图和评测组件。图通过注入回调记录执行步骤，减轻图层与日志存储之间的耦合，但节点调用的模型配置与工具仍依赖业务数据库。

4.2 为什么使用两个数据库

MySQL 保存业务实体、文本片段、配置、对话和评测。PostgreSQL 使用 pgvector 保存向量，以及知识库、文档、父块等过滤字段。两边通过 chunk_id 关联，查询结果再按需要回查文档名称。

这样做便于业务 CRUD 与向量能力分别维护，但引入跨库一致性、两套连接管理和运维成本。源码无法证明它优于单一 PostgreSQL 方案；对于新建的小规模应用，合并存储也可能更简单。这里应解释现有设计及其代价，不把技术数量当作架构水平。

5 技术方案与设计依据

5.1 多格式文档解析

白话理解：这是把 Word、PDF、表格和扫描图片等不同“包装”的资料，拆出后续检索能处理的文字。它负责读出内容，不代表已经理解了表格含义或还原了原文件的完整版面。

解决的问题：文件中的内容不一定是可直接读取的纯文本，尤其是 PDF 表格和扫描页。

如何实现：PyMuPDF 读取 PDF 文字，pdfplumber 抽表格，无文字层的页面渲染为图片交给 RapidOCR。Word 使用 python-docx，Excel 使用 openpyxl，TXT 和 Markdown 直接读取。表格统一转换成 Markdown，PDF 加入页码标记。

为什么这样设计：统一文本输出可以让后续切分和向量化不必理解各种文件格式；Markdown 比散乱字符更容易保留行列关系。

边界：Word 的正文与表格分别遍历，原文穿插顺序未完整保留；OCR 不是版面理解系统；PDF 文字与表格可能重复；Excel data_only=True 读取缓存计算结果，不会执行公式计算。页码属于简化标记，不等于精确的跨页坐标溯源。

代码入口：loader.py 第 82 行 。

5.2 递归分块与父子分块

白话理解：一本手册不能每次搜索都整本搬出来，也不能切成失去上下文的一句话。子块像目录卡片，负责精准命中；父块像卡片对应的完整段落，负责给模型补齐条件和背景。

解决的问题：全文过长，片段太大容易混杂主题，片段太小又丢失条件和上下文。

如何实现：递归切分优先尝试段落、换行和中文标点，再按字符切分兜底。父子策略先生成不重叠的大父块，再在各父块内生成可重叠子块。写库时先插父块，把列表下标映射成真实 parent_id。

为什么这样设计：小子块承担检索，大父块承担生成；同一父块下多个命中子块合并后，减少重复资料。父块不向量化，可以避免重复存储和父子共同参与召回。

取舍：父块会引入更多无关文字和 token 成本，不能越大越好。切分按字符数计量，最终上下文预算仍需要考虑模型 token 限制。

代码入口：splitter.py 第 109 行 、父块回填 第 424 行 。

5.3 向量与 BM25 混合检索

白话理解：可以把它看成两种搜索员同时找资料：一个理解“保修”和“质保”意思相近，另一个擅长准确查找 GTE-3000 这样的字符。RRF 根据两位搜索员各自的名次汇总结果，避免把不同单位的分数硬加在一起。

解决的问题：语义检索可以匹配同义表达，但可能弱化型号、错误码等精确字符；关键词检索可以匹配字符，但不擅长同义表达。

如何实现：问题编码为向量，在 PostgreSQL 按知识库、文档和片段类型过滤，再按余弦距离排序。BM25 从 MySQL 读取普通块和子块，使用 jieba 与型号补充分词，在内存计算排名。多份非空榜单通过 RRF 按 chunk_id 融合。

为什么这样设计：两路互补；RRF 避免直接比较含义和尺度不同的原始分数。当前融合结果条数取两路 top_k 的最大值，不是无限保留两路并集。

边界：向量表固定为 vector(1024)，SQL 建立 IVFFlat 索引，但实际是否使用索引要看执行计划。BM25 每次重建索引，候选上限为 5000，超出部分可能不参与检索。各路及各查询目前顺序执行。

代码入口：检索主流程 第 172 行 、BM25 与 RRF 第 56 行 、向量索引 第 247 行 。

5.4 重排与分数量纲

白话理解：混合检索先从大量资料里圈出一批“可能有用”的候选；Rerank 再拿具体问题逐条比较，调整先后顺序。它能重新排序已找到的内容，但不能凭空找回第一轮完全没召回的资料。

解决的问题：语义相似不一定意味着能回答问题；候选资料顺序也会影响生成。

如何实现：DashScope 原生接口接收问题与候选文本，返回索引和相关性分数，代码再映射回原片段。重排位于 RRF 后、父块回填前。

为什么这样设计：重排比粗召回成本高，先减少候选，再精排；对子块精排能够保留更集中的匹配对象，随后补上下文。

阈值原则：使用 score_scale 标识最终分数类型，余弦相似度与重排分分别配置阈值，BM25 和 RRF 不套用固定相关性阈值。余弦相似度数学范围是 [-1, 1]，源码中的“0 到 1”注释并不严谨；本项目允许配置的向量阈值范围为 0 至 1。

代码入口：reranker.py 第 29 行 、阈值处理 第 330 行 。

5.5 查询改写与多轮问答

白话理解：用户说“那它过期了怎么办”，单看这句话可能不知道“它”指什么。查询改写会在检索前把问题补完整或换成更容易命中文档的表达；它改变的是搜索用的问题，不自动等于模型已经记住完整聊天历史。

解决的问题：口语问题与文档写法不同；“它”“那种情况”缺少独立检索信息。

如何实现：多查询扩展保留原问题并添加其他表达；指代消解根据历史补全问题；HyDE 生成假设答案，将其与原问题拼接用于检索。普通问答随后拼接资料与问题，使用 astream 输出增量。

为什么这样设计：改写在检索前修正输入，引用在生成前推送，正文完成后发出结束事件。引用保存内容快照，便于回看当时的依据。

边界：历史主要进入指代消解，不直接进入最终生成 Prompt；普通模式开关未启用指代消解时，省略表达可能仍然检索失败。上下文按字符预算组装，遇到下一块放不下时停止，没有完整的 token 预算与智能截断机制。引用集合也不等于答案中每个句子已经验证过来源。

代码入口：查询改写 第 42 行 、普通问答 第 193 行 、前端 SSE 第 26 行 。

5.6 Agentic RAG 条件工作流

白话理解：普通 RAG 像查一次资料就作答；这里的 Agent 流程像一张预先画好的检查清单：先查资料，再判断是否相关；答案生成后，再检查有没有资料支撑。检查不通过就按规则重试，超过次数则停止并给出兜底结果。

解决的问题：普通 RAG 只检索和生成一次，难以处理召回不相关或答案缺乏依据的情况。

如何实现：LangGraph 定义状态和六个节点，条件边根据 is_relevant、is_grounded 和计数决定重试或终止。第一轮无历史时使用原问题，有历史时先做指代消解；不相关后再改写。持续不相关时，第 3 次失败后兜底；持续无支撑时，第 2 次失败后兜底。

为什么这样设计：把控制流程写在图中，便于解释分支和单独检查流程。数据库记录步骤，SSE 推送进度，让等待过程可见。

边界：工具由代码固定调用，尚无完整的自主工具选择循环；只检索 kb_ids[0]，使用全局默认检索策略；图内模型与 Prompt 也没有继承全部应用配置。MAX_GRAPH_STEPS = 10 被用于计算 recursion_limit = 30，不是严格的十节点业务计数保护。步骤日志的耗时当前写为 0。未配置持久化 checkpointer。

代码入口：状态图 第 243 行 、Agent 执行 第 96 行 、工具实现 第 22 行 。

5.7 评测与反馈闭环

白话理解：不能只看一两个演示问题就判断系统变好了。评测把一组固定问题反复交给系统，分别检查“该找的资料有没有找着”“答案有没有依据”“答案有没有答到问题”，再结合耗时和成本看改动是否值得。

解决的问题：单次演示不能证明策略有效，用户反馈也需要进入可重复的回归流程。

如何实现：评测集来自人工录入、文档生成和点踩沉淀。点踩用例默认停用且标准答案留空，人工补充后启用。批量任务按策略检索、生成、计算四项指标，再汇总报告，保存策略快照。当前每批最多 20 条启用用例。

指标计算对象当前实现
Context Recall标准答案或参考片段参考 ID 命中比例，或标准答案陈述的资料支撑比例
Context Precision排序后的召回资料判断相关性，对相关位置的累计精确率取平均
Faithfulness生成答案答案陈述的资料支撑比例
Answer Relevancy问题与答案从答案反推一个问题，再与原问题计算向量相似度

为什么这样设计：把“资料没找到”和“资料找到但回答不好”分开诊断。参考 ID 可以减少部分裁判模型调用，报告快照帮助解释当时的策略。

边界：这是自定义实现，并非直接调用 RAGAS。问答与裁判使用同一条全局对话模型配置；temperature = 0 不能保证绝对确定性。评测主要覆盖普通 RAG，没有直接运行完整 Agent 图。裁判配置、Prompt 和用例没有完整冻结成可重现版本。

代码入口：evaluator.py 第 162 行 、评测任务 第 122 行 、反馈沉淀 第 311 行 。

6 由浅入深的模拟面试

每组按顺序提问。答案采用“当前实现、设计理由、边界或改进”的顺序，涉及未实现能力时明确使用“如果改造”。你应理解后用自己的话回答，不要把参考答案中的项目事实改写成未经实践的个人成果。

第一组 项目理解与个人工作

考察重点：能否说清业务目标、技术选择和个人贡献。

Q01 请介绍一下这个项目

参考答案：这是企业知识库问答平台，解决资料格式杂、查找困难和回答缺乏依据的问题。离线把文档解析、切分并向量化；在线通过向量和关键词检索、融合及重排获取资料，再生成回答。平台还有 LangGraph 条件工作流、引用、反馈和评测，能够支持对检索与回答效果的分析。

Q02 为什么选择 RAG 不直接把资料放进 Prompt 或微调

参考答案：全文放入 Prompt 会随着资料量增加带来上下文限制和调用成本，也难以定位相关内容。RAG 只取相关资料，更新知识主要重建索引，不必训练模型。微调可以改善行为、格式和特定任务表现，但不能简单替代可更新、可追溯的知识检索。选择仍取决于任务，不能声称 RAG 在所有场景都优于微调。

Q03 这里面你具体负责了什么

参考答案：必须按实际阶段回答。目前只有研读时，可以说：“这是第三方项目，我重点研究检索管线、Agent 编排和评测，尚未把原项目实现当成自己的开发成果。”完成改造后，再说明具体问题、修改文件和回归结果。不要用“负责整个架构”替代个人证据；面试官通常会继续追问一处具体决策或失败案例。

Q04 为什么选 FastAPI LangChain 和 LangGraph

参考答案：FastAPI 提供异步接口、参数校验和依赖注入，适合编排数据库与模型的网络调用。LangChain 相关组件减少模型与切分器的适配代码。LangGraph 把状态和条件流程显式表达，便于管理重试与终止。它们不是必需品，固定短流程也可以手写；选择框架的价值应是减少当前复杂度，而不是增加技术栈数量。

Q05 两个数据库是不是过度设计

参考答案：现有系统将业务数据放 MySQL、向量放 PostgreSQL，职责明确，但有跨库一致性和运维代价。如果是新建应用且没有 MySQL 约束，单一 PostgreSQL 可能更简单。我会先确认业务已有基础设施、数据规模和运维能力，再决定是否拆分。不能仅凭源码证明双库方案更快或更可扩展。

第二组 文档处理与知识更新

考察重点：能否从文件格式深入到分块、一致性和失败恢复。

Q06 文件上传后如何变成可查询知识

参考答案：文件先保存到本地，再创建知识文档记录。管理员分别触发解析、切分和向量化。解析产出统一文本，切分生成普通块或父子块，普通块与子块分批调用 Embedding 并写入 pgvector，MySQL 更新状态与计数。当前是分阶段触发的后台任务，不是上传后自动串联的完整任务流水线。

Q07 PDF 表格和扫描页怎么处理

参考答案：PDF 文字由 PyMuPDF 提取，表格由 pdfplumber 转成 Markdown。整页没有文字层时渲染为图片，使用 RapidOCR 识别。这样的输出能复用后续文本切分，但复杂版面、合并单元格、混合图片页和表格重复都需要真实样本验证。不能把“能提取文字”理解成“完整还原版面和业务语义”。

Q08 chunk_size 和 chunk_overlap 怎么选

参考答案：先根据文档类型和问题粒度确定候选范围，再用固定评测集比较召回、答案质量、上下文长度和延迟。小块可能更聚焦但丢失条件，大块更完整但噪声更多，重叠能保护边界但增加重复。当前实现按字符长度切分，所以参数不能直接当 token 数。没有普适最佳值，应保留选择依据和对照实验。

Q09 为什么父子分块 直接把所有块变大不行吗

参考答案：大块中的多个主题会稀释向量表达，而小块可能缺少回答所需条件。父子分块让子块承担匹配、父块承担上下文。项目先对子块召回和重排，再按 parent_id 回填父块，同父块去重。代价是父块噪声与 token 成本，因此仍需验证回填是否改善回答，不能假设开启后必然更好。

Q10 文档更新后如何避免检索旧知识

参考答案：理想流程要让旧片段和旧向量同时失效。当前源码存在缺口：重新解析只重置状态，没有删除旧数据；后续切分又按文档状态决定是否清向量，因此可能留下旧向量。最小修复需要明确旧向量清理与失败状态；更完整的方案是为文档、片段和向量增加版本，构建成功后切换可检索版本。验收应覆盖更新、失败、重复执行和重启。

代码核对：解析完成处理 第 57 行 、重新切分 第 94 行 。

第三组 混合检索与排序

考察重点：能否讲清算法作用、实际 SQL、分数和性能边界。

Q11 向量检索是怎么实现的

参考答案：先用 Embedding 模型把问题编码，再在向量表限定知识库、文档和普通块或子块，用 <=> 计算余弦距离，升序取 Top K。返回分数为 1 - distance。向量维度固定为 1024，脚本建立 IVFFlat 索引，但 SQL 有索引不代表执行时一定使用，性能需要执行计划和实测。

Q12 为什么 Embedding 模型不能随便换

参考答案：模型不同，向量所在的语义空间可能不同，即使维度相同也不能直接比较。项目在向量化时绑定知识库与模型，但查询仍使用全局启用模型，保护不完整。改造时应按知识库绑定的模型生成查询向量，并处理跨模型知识库；模型版本也应纳入约束，不能只比较一个可被修改的配置 ID。

Q13 为什么向量检索还需要 BM25

参考答案：型号、错误码和专有词需要精确字符匹配，语义模型可能把它们当成接近的概念。BM25 能补足这些召回。项目针对 GTE3000 等连写词补充字母和数字分词，使其与 GTE-3000 对齐。BM25 也不是天然正确，例如中文分词、同义词和高频词都影响结果，所以两路互补并通过评测验证。

Q14 两路分数为什么不加权相加 RRF 怎么算

参考答案：BM25 与余弦相似度尺度不同，未经校准直接加权可能使一路支配结果。RRF 使用各榜单排名，某片段贡献为 1 / (k + rank)，多路出现就求和。以 k = 60 为例，两个榜单分别第 1 与第 3，分数约为 1/61 + 1/63 = 0.03227。它弱化分数尺度问题，但也丢弃原始分差，不是必然最优。

Q15 已经融合排名 为什么还要 Rerank

参考答案：粗召回回答“可能相关吗”，重排进一步判断“对这个问题有多相关”。项目把问题和候选文本送到远程重排服务，再按返回索引映射原片段，保留前 N。它增加网络调用和成本，因此适合少量候选。若候选召回根本没有答案，重排也无法补回，所以先看召回，再优化排序。

Q16 为什么要区分 score_scale

参考答案：score 会被各阶段覆盖，可能代表余弦相似度、BM25 分数、RRF 排名分或重排分。若统一设置 0.3 阈值，两路 RRF 分数常在百分之几，可能被全部过滤。项目显式传递量纲，分别使用向量和重排阈值，BM25 与 RRF 不应用固定相关性门槛。即使两个分数都在 0 至 1，也不能默认含义一致。

Q17 上万甚至百万片段 当前检索还能用吗

参考答案：不能直接承诺。BM25 每次读取最多 5000 条并重建内存索引，既有性能成本，也可能漏掉上限外的答案。向量连接每次新建，召回顺序执行，也需要优化。先建立数据规模和延迟基线，检查 SQL 与索引，再考虑持久化关键词索引、连接池和有界并发。这些是改造方向，不是当前代码能力。

代码核对：模型选择 第 149 行 、召回与融合 第 172 行 。

第四组 查询理解与对话交互

考察重点：能否解释模型输入、对话上下文、流式协议和引用含义。

Q18 多查询扩展和指代消解有什么区别

参考答案：多查询扩展针对同一意图生成不同表达，扩大召回覆盖；指代消解结合历史补全当前省略问题，使其独立可检索。项目的多查询保留原问题，指代消解在没有历史时直接返回原问题。两者目的不同，不能说“有历史消息表就已经解决多轮理解”。

Q19 HyDE 生成假答案 会不会把错误带进回答

参考答案：项目将假设答案与原问题一起用于检索，不把它直接作为最终回答资料。它希望生成内容在表达上更接近文档，但可能引入错误术语或改变检索方向。最终回答仍应依赖真实召回资料，并对 HyDE 单独做对照评测。它是一种候选策略，不能因增加一次模型调用就认为效果一定提升。

Q20 多轮对话历史到底在哪里使用

参考答案：历史从会话消息表读取，主要供指代消解使用。普通生成 Prompt 只接收资料和当前问题，没有把完整历史直接传进去，所以用户要求“沿用上一轮格式”这类需求不一定得到满足。如果改造，应明确历史窗口、问题改写结果和生成消息输入，按 token 控制预算，并避免重复提问被内容过滤逻辑误删。

Q21 为什么用 SSE 不用 WebSocket

参考答案：这里主要是服务端向浏览器推送进度和答案，SSE 足够满足单向流式需求。问答接口是 POST 且需 token 头，所以前端用 fetch 读流而不是原生 EventSource。普通模式发正文增量；Agent 模式发节点进度，校验完成后一次性发最终答案。若需要语音等持续双向交互，再评估 WebSocket。

Q22 有引用是否就能保证答案正确

参考答案：不能。引用证明本次取得过哪些资料，内容快照能保留历史依据，但模型可能误读、混合条件或写出资料未支持的细节。还要检查引用是否真正进入生成上下文、答案句子与资料是否对应，以及资料本身是否有效。项目的引用记录与上下文截断也需要对齐，不能把所有召回资料都视为实际使用过的证据。

第五组 Agent 状态编排与工具调用

考察重点：能否区分条件工作流与自主 Agent，并解释终止、恢复和权限。

Q23 这个 Agent 相比普通 RAG 多了什么

参考答案：普通模式检索一次后生成。Agentic 模式增加资料相关性判断和答案支撑检查：不相关则改写重检索，无支撑则重新生成，达到失败上限则兜底。它改变的是执行控制和质量检查，复用的仍是原有检索能力。我会称它为 Agentic RAG 条件工作流，不把它说成通用自主规划 Agent。

Q24 LangGraph 的状态 节点和条件边分别是什么

参考答案：状态保存当前问题、资料、答案和计数等执行上下文。节点完成一次操作并返回状态更新，例如检索节点更新文档和次数。条件边读取状态决定去生成、重试或兜底。这样数据与控制关系明确，但节点是否可恢复、结果是否可重放仍需要额外设计，画出图本身不能解决可靠性。

Q25 模型不按要求输出相关或不相关怎么办

参考答案：当前代码通过包含关系判断“相关／不相关”和“有支撑／无支撑”，先排除否定词，未识别为通过就按失败处理。这种文本解析比较脆弱。如果改造，可以采用受约束的结构化输出，校验枚举与字段，记录解析失败，有限重试后保守终止。还应避免把格式失败和真正不相关混为同一指标。

Q26 如何防止 Agent 无限循环和费用失控

参考答案：项目有失败次数限制、上下文字符上限和框架递归限制，但没有完整 token、费用或总时间预算。持续不相关到第 3 次失败后兜底，持续无支撑到第 2 次失败后兜底。MAX_GRAPH_STEPS = 10 实际用于计算递归限制 30，不能说严格最多十个节点。改造应统一检查调用次数、总时长和预算，并对取消与超限定义终止结果。

Q27 它有没有实现自主 Function Calling

参考答案：没有完整实现。状态图固定调用 search_knowledge，模型负责相关性和支撑判断，没有读取多个工具后自主选择。工具中心存在注册、开关和定义预览，但不能据此宣称自主调用已接入。应依据实际运行路径回答，而不是根据函数名或管理页面判断功能。

Q28 如果让模型自主选择工具 你如何改造

参考答案：先定义完整工具 schema 和执行范围，再把允许的工具绑定到模型。模型返回 tool calls 后，由应用校验工具名、参数和用户权限，执行工具，并以对应 tool_call_id 回传结果，直到模型产出最终答案或达到预算。项目当前定义转换把参数都声明为字符串，缺少完整类型与必填约束，需要先修正。模型决定“请求什么”，应用仍决定“允许执行什么”。

Q29 应用挂多个知识库 Agent 会都检索吗

参考答案：当前不会，检索节点只取 kb_ids[0]，工具内部还使用全局默认策略。普通模式可传多个知识库，Agent 模式没有继承同样的范围和配置。如果改造，应在执行上下文中显式传递知识库集合、检索策略、模型和 Prompt，并在工具侧验证权限。用答案只在第二个库的测试，可以暴露这类差异。

Q30 能否暂停 Agent 后继续执行

参考答案：当前图没有配置持久化 checkpointer，数据库里的 AgentStep 是日志，不是可恢复检查点。增加恢复能力时，需要持久化状态、执行身份与版本，并设计节点幂等，避免恢复后重复执行工具。涉及外部写入的工具还需要操作幂等键与结果确认。仅有历史步骤记录不能直接声称支持断点续跑。

代码核对：固定工具调用 第 121 行 、工具 schema 第 109 行 、执行上限 第 126 行 。

第六组 效果评测与实验设计

考察重点：能否证明改动有效，并识别评测定义与偏差。

Q31 如何判断一次优化有没有效果

参考答案：准备固定且人工核对的评测集，包含型号、同义表达、跨条款、多轮、省略和无答案问题。固定模型、Prompt、知识版本等条件，每次只改变一个主要变量，比较四项指标及延迟、调用成本、失败和拒答情况。还要抽样审查答案，避免仅看平均分。当前项目提供了评测入口，但没有足够证据可直接报个人提升数字。

Q32 四个评测指标分别测什么

参考答案：Context Recall 看标准答案所需信息是否被召回；Context Precision 看有用资料是否排在前面；Faithfulness 看答案陈述是否有资料支撑；Answer Relevancy 看答案是否回应原问题。项目分别使用参考片段或陈述判断、相关位置的累计精确率平均、陈述支撑比例、反推问题后的向量相似度，是自定义实现。

Q33 Context Precision 是相关条数除以总条数吗

参考答案：项目不是这样算。它在每个相关位置计算截至该位置的精确率，再对所有相关位置取平均。例如 [相关, 不相关, 相关] 的分数为 (1/1 + 2/3) / 2 = 0.8333。有用资料越靠前越占优。不过 [相关, 不相关, 不相关] 会得 1，说明它对尾部噪声的惩罚有限，应配合其他噪声和成本指标解释。

Q34 为什么开启父块回填后召回分数可能反而下降

参考答案：评测用例可能记录的是子块 ID，但回填把最终结果的 chunk_id 换成父块 ID，直接取集合交集会漏记实际命中。因此要分开记录“用于匹配的子块”和“用于生成的父块”，再定义统一评测口径。重新切分也会改变 ID，参考标注需要版本或稳定标识。先排除测量问题，再讨论检索质量下降。

Q35 使用同一个模型生成和评分可靠吗

参考答案：有偏差风险。模型可能对自身生成风格更宽容，自动生成的用例也可能偏向简单问题。项目用同一全局对话配置进行生成和裁判，温度为零仍不保证完全稳定。应加入人工标注、不同来源问题、独立裁判或抽样复核，并记录重复评测波动。裁判分数是辅助证据，不是客观真值。

Q36 当前评测能证明 Agent 更好吗

参考答案：不能直接证明。批量任务调用普通检索和生成，没有运行完整 Agent 图。要比较 Agent 与普通模式，应保持知识与模型条件一致，对两种链路端到端执行，同时记录回答质量、检索次数、模型调用、总时长、兜底和失败率。Agent 增加检查可能改善质量，也可能增加成本和延迟，必须测量这个取舍。

代码核对：指标计算 第 135 行 、批量评测入口 第 122 行 。

第七组 生产工程与失败路径

考察重点：能否从功能演示深入到安全、并发、恢复和可观测性。

Q37 BackgroundTasks 能否承担可靠文档处理

参考答案：它适合简单的进程内后台操作，响应发出后执行，但服务重启或崩溃可能中断任务。任务表能记录状态，不能替代持久化队列。生产改造应定义任务领取、原子状态转换、超时、重试、幂等和失败恢复，再根据规模选择数据库任务表或独立队列。具体组件不是重点，可靠语义才是重点。

Q38 两个人同时触发同一文档处理 怎么办

参考答案：“先读状态、再更新状态”的校验可能同时通过，按钮禁用也挡不住并发请求。当前解析与向量化有状态检查，切分的重复处理保护也不完整。如果改造，应使用条件更新或锁实现原子领取，并约束同文档互斥阶段和处理版本。测试用并发请求验证只有一个任务实际获得执行权。

Q39 向量化一半失败了怎么办

参考答案：当前每批 10 条，模型调用失败就标记这一批失败并继续其他批次，最后汇总文档和任务状态。upsert 避免重复插入，但再次执行会遍历全部可检索片段，并非只重试失败块。改造可按版本与状态选择待处理批次，同时校验返回向量数量和维度，并区分模型失败、向量写入失败和业务状态回写失败。

Q40 MySQL 与 PostgreSQL 如何保证一致

参考答案：当前没有跨库原子事务，可能出现向量写入成功但业务状态更新失败，或旧向量清理与片段删除不同步。对于当前范围，可以先明确操作顺序、幂等和补偿，再加入版本及定期对账。查询只读取发布成功的版本可以减少半成品暴露。不能因为有状态字段就声称已经解决最终一致性。

Q41 用户或文档试图让 Agent 越权 怎么处理

参考答案：权限必须在应用与工具执行层校验，不能依赖 Prompt。项目对管理接口和会话归属做了鉴权，但文件上传下载没有鉴权，密码直接存储比较；资料也可能包含恶意指令。改造要落实文档范围校验、密码哈希、文件名与路径限制，明确资料是不可信数据，并对工具参数和操作进行服务器端授权。模型判断不能授予权限。

Q42 用户说回答很慢 你怎么定位

参考答案：先分解问题改写、Embedding、向量查询、BM25、重排、生成与 Agent 裁判调用的耗时，并记录首个正文事件与最终完成时间。普通模式与 Agent 模式不能混在一起比较。项目有检索阶段和总耗时，但 AgentStep 耗时为零，token 字段也没有在当前问答链路完整采集。需要补齐测量，再针对瓶颈做连接复用、有界并发或调用裁减。

代码核对：任务触发 第 16 行 、步骤记录 第 26 行 、账号处理 第 32 行 、文件接口 第 12 行 。

第八组 深入追问与个人证据

考察重点：能否选择有价值的问题，设计可复现验证，并如实表达结果。

Q43 如果只让你改三处 你会优先改哪里

参考答案：我会先处理查询模型与知识库绑定不一致、知识更新后旧向量残留、Agent 知识库和应用配置传递缺失。这三项影响回答所基于的数据与范围，比先增加更多工具更基础。针对 Agent 岗位，基础问题解决后，再增加严格工具 schema 和自主调用循环。优先级应由正确性、用户影响和验证成本决定。

Q44 你如何证明这些问题确实存在并已经修复

参考答案：先写失败用例。例如旧库用模型 A 向量化，切换全局模型 B 后查询；文档先产生一个旧条款，更新并重新解析切分，再查询旧条款；把答案只放在第二个知识库，运行 Agent。保留修复前失败和修复后通过的证据，还要覆盖无答案、任务失败和重复执行。本文只做静态分析，所以尚不能声称这些运行测试已经完成。

Q45 如果面试官问上线规模和提升数字 你怎么回答

参考答案：按实际证据回答。没有上线就说明是研究或本地实践，交代数据来源与规模；没有前后对照就不报提升百分比。完成实验后，应说明评测集、模型、策略、重复次数、指标定义和成本变化。一个范围明确、能复现的改造，比无法解释来源的“准确率提升百分之三十”更有说服力。

7 将研究转化成可写进简历的实践

以下均为待实践方案，本文没有实施业务代码改动。

7.1 实践一 修复检索正确性

目标是确保查询模型空间一致，更新后的知识不会与旧知识混合。先准备能暴露问题的最小知识库，再修复模型绑定查询和旧向量失效逻辑。验收覆盖全局模型切换、同维度不同模型、文档更新、重复处理和处理中失败。

交付证据包括失败复现记录、最小代码改动、必要回归测试和更新前后的检索结果。涉及版本字段或 schema 的方案应先明确范围，再实施。

7.2 实践二 补足 Agent 应用配置与工具执行

第一阶段先让 Agent 使用应用挂载的全部知识库、策略、模型和 Prompt，避免普通模式与 Agent 模式行为分叉。第二阶段再接入模型自主工具调用，补完整 schema、参数校验、权限、调用结果关联、超时与预算。

验收至少包含：答案仅在第二个库；指定策略与默认策略明显不同；未知工具；错误参数；停用工具；越权文档；工具失败；持续请求工具达到上限；正常终止。断点恢复属于额外能力，需要检查点和幂等设计，不能顺带宣称已经具备。

7.3 实践三 建立端到端效果对照

准备人工确认的用例，包含型号、同义表达、跨条款、表格、多轮和无答案问题。在固定知识版本下比较向量基线、混合检索、重排、父块回填和 Agent；校正父子 ID 评测口径。

记录质量、拒答、异常、耗时和调用成本，人工复核部分结果。当前每批上限为 20，可以拆成多个固定批次并统一汇总，不应为了跑大评测直接绕过既有预算保护。报告中要保留失败数量，避免只统计成功样本产生幸存者偏差。

7.4 实践记录模板

字段应填写的证据
